1. 為什麼要做逆向工程

系統上線多年、經過多次需求修改後，「文件寫的」與「程式做的」常常不一樣。要回答「這個頁面到底會擋什麼、為什麼擋」，最可靠的答案只在源碼裡。

我們遇到的問題

痛點實際情況後果
規模龐大規格文件 1,896 份、Java 5,076 支、JSP／XHTML 2,411 支、選單功能 1,331 個沒有人能全部掌握，跨模組問題從零查起
名詞不對應「限制異動需主管授權」在源碼中有 3 套不同機制問人、追程式動輒 30 分鐘以上，還可能答錯
文件與程式落差多次需求修改（MR）後，程式行為與原規格描述不一致相信文件反而踩坑
文件只寫意圖規格寫「需檢查信用」，但沒寫查哪些、哪裡會擋、擋了顯示什麼知道 what，不知道 how
新人上手慢到職 3～6 個月才能獨立處理訓練成本高、資深同仁被反覆打斷

傳統規格文件 vs Page Spec

比較傳統 SRS／SDSPage Spec（逆向文件）

時效可能過時或與實作不符與當前源碼同步，可定位到行
重點著重「為什麼」著重「怎麼做」，再用 SRS 補充「為什麼」
撰寫者SA／PMAI ＋ 工程師從源碼逆向撰寫

誰會用、怎麼用

角色以前有 Page Spec 後
開發開 IDE 搜關鍵字、追呼叫鏈、再問人確認查規則 → 看源碼定位 → 直接改，約 5 分鐘掌握邏輯
業務／客服「為什麼被擋？」要等開發回推判斷條件查失敗訊息欄，直接找到規則與業務原因
QA依規格寫測試案例，常漏掉程式裡的例外分支依阻擋規則（R）逐條設計案例，含例外與複核
新人口頭解釋 30 分鐘，下次還要再講丟一份連結：導覽 → 術語 → 主頁面，自學

2. 核心精神：七大準則

Page Spec 的本質是逆向工程文件：從既有源碼還原系統的真實流程與邏輯，而不是從需求文件正向推導。

準則說明
1. 源碼為主要事實來源規則、判斷邏輯、欄位、分支都以實際 Java／JSP 源碼為依據；SRS／SDS 只補充業務背景與命名由來。
2. 行為優先於意圖記錄系統實際做了什麼，而不是規格希望它做什麼。源碼與文件不一致時以源碼為準，並標註差異。
3. 逐行可追溯每條規則都標註程式與位置，讀者能直接在 IDE 驗證；不接受「依規格推導」的無定位描述。
4. 忠實還原，不美化冗餘邏輯、歷史補丁、寫死的條件都照實記錄，不因「不優雅」而省略或重組。
5. 分層記錄記錄完整呼叫鏈：畫面 → 頁面事件處理 → 業務委派 → 業務邏輯 → 資料存取，包含中間的判斷與分支。
6. 區分確定與推測讀過源碼驗證的標 ✅；推測或由文件推導的標 ⚠ 待驗證，讓讀者判斷可信度。
7. 增量探索不求一次完備：先建骨架（頁面結構＋呼叫鏈），再逐方法深入，每次深入就更新驗證狀態。

事實來源優先序

優先來源用途信任度
1源碼（Java／JSP／SQL）規則邏輯、判斷條件、欄位綁定、呼叫鏈🟢 最高（唯一事實）
2DB Schema＋實際資料表結構、欄位值域、代碼實際有哪些值🟢 高（可直接查詢驗證）
3UI 畫面（源碼 HTML）欄位佈局、顯示條件、事件綁定🟡 中（需對照後端屬性）
4SRS／SDS／SWDS業務背景、命名由來、修改歷史🟡 輔助（可能與源碼不一致）
5推測／命名推導—🔴 最低（必須標 ⚠）

4. 製作流程：6 步

原則是「AI 做苦工、人做決定」：每一步都有明確的人工把關點。

  1. 定位頁面：用業務關鍵字查知識庫，找出入口、子頁與呼叫鏈。例：「信用查核會查客戶風險、欠費、戶役政，請用這些項目找到信用查核頁面」→ 找到 che***it 套件與 5 個 chk***sk 子頁。把關：前後端源碼都在庫嗎？
  2. 先規劃，審核後再撰寫：請 AI 依格式範本提出範圍、頁面清單、規則草估與待確認問題。例：「是否包含 NP 攜入新申裝？否」「規則數是否設上限？否，以完整、正確為優先」。把關：範圍與頁面清單正確嗎？
  3. 由 UI 觸發點窮舉規則：讀每頁 JSP，列出所有按鈕、下拉、連結觸發的方法，逐方法讀判斷分支。產出 UI 觸發點清單與規則清單。把關：每個阻擋點都有對應規則嗎？（詳見第 5 節）
  4. 依範本撰寫：全局導覽、頁面說明、依源碼 HTML 繪製的 UI 模擬圖、欄位、規則卡（業務語言＋三重定位＋流程圖）。把關：業務看得懂判斷邏輯嗎？開發找得到程式嗎？
  5. 標示驗證狀態：逐項標 ✅ 已從源碼驗證／⚠ 待驗證，寫明誠實界線。例：v0.1 盤點 18 條規則、6 項 ✅、5 項 ⚠。把關：有沒有拿推論冒充事實？
  6. Review 迭代、通過才入庫：逐項消化 ⚠、補對外介面章節、更新文件歷程；審核通過才匯入知識庫，避免草稿污染。例：v0.2 補齊 4 項實證、1 項誠實澄清為「人工判斷、無 API」。

5. 規則盤點方法：由 UI 觸發點往下窮舉

規則的正確性與完整性必須是 100 分。盤點不依賴 SRS／SDS 的規則清單，而是從畫面元件出發，窮舉所有可觸發的判斷邏輯。

步驟動作產出
1. 讀 JSP 全文列出每個 valueChangeListener、action、actionListener、window.open、onclickUI 觸發點清單（含行號）
2. 分類觸發點區分「含判斷邏輯」與「純查詢／純畫面導向」需寫規則的方法清單
3. 逐方法讀源碼讀每個 if／return／continue，找出所有判斷分支每個方法的判斷步驟表
4. 寫規則每個含阻擋／過濾／重算的方法＝一條規則；大方法用步驟表列出內部判斷完整規則文件

分層追呼叫鏈

flowchart LR P["JSP 畫面觸發"] --> B(("BackingBean 事件處理")) B --> H(["BD／Helper 委派"]) H --> E["EJB 業務邏輯"] E --> D[("DAO／SQL 資料存取")] H --> X{{"外部系統 API"}}

追鏈時順手記下每一層的「呼叫者」與「被呼叫者」。最後回頭核對：每個子頁的每個觸發點，都要能在 Bean 找到對應方法，並對到一條規則或「不需寫規則」的理由。

完整性標準

  • 必須寫規則：畫面上每個會觸發後端方法的元件，只要方法內有「顯示訊息後 return」等阻擋點，就要有對應規則。
  • 不需寫規則：純查詢顯示、純畫面導向（如返回）、純計算且無阻擋。

規則粒度

方法規模寫法範例
小（< 30 行，1～3 個判斷）一條規則，判斷邏輯用編號清單驗證主約編號（2 步）
中（30～100 行，3～9 個判斷）一條規則，用步驟表（# / 檢查名稱 / 條件 / 源碼定位 / 失敗處理）選擇產品（9 步）
大（100 行以上，10 個以上判斷）仍寫成一條規則，步驟表＋分群；流程圖畫分群不畫逐步新增優惠驗證（28 步）

同一頁的規則依使用者操作時序由上而下排列，不按 R／F／D 分組。讀者想知道的是「操作到這一步時，系統會檢查什麼」。

8. 寫作規範：寫業務規則，不是翻譯程式

最常見的失敗，是把程式碼換成中文就當成規則。判斷條件要讓業務、QA、開發都看得懂；程式細節移到「源碼來源」欄。

❌ 翻譯程式判斷條件：ifShowIMEI==true && (serial_no==null || serial_no.trim().length()==0)
✅ 業務語言判斷條件：此優惠包含保險／電池服務，需輸入 IMEI，但使用者未輸入 IMEI／序號。
❌ 只寫結果風險等級不符時回傳錯誤。
✅ 三層描述①客戶命中須複核的風險種類時 ②對中度風險客戶要求主管把關並留下軌跡 ③要求輸入具複核權限的主管，未複核不得受理。
❌ 改寫訊息失敗訊息：提示風險不可受理。
✅ 逐字引用失敗訊息：「此客戶的風險種類，系統不予受理！」
欄位放什麼不放什麼
判斷條件業務語言；代碼值可保留但附中文說明程式語法、變數宣告、比較運算子
失敗訊息使用者看到的逐字訊息自行改寫或摘要
源碼來源方法名＋搜尋關鍵字＋基線行號—

流程圖規則

  • 判斷用菱形；成功出口標「通過」，失敗出口標「踢錯」或「過濾」。

10. 實戰歷程：方法是怎麼長出來的

格式範本不是一開始就設計好的，而是在對話中邊做邊修、再把好的做法沉澱下來。

  1. 建知識庫：匯入規格文件與約 1.5 GB 源碼到 MongoDB，可語意搜尋、全文搜尋、追程式鏈。
  2. XG 互轉試寫：「給定作業名稱，盤點頁面、欄位與檢查規則；規則從源碼回推為業務說明，再輔以 SRS／SDS」。過程中追加：UI 示意參考源碼 HTML、補文件歷程章、P4 缺圖補上。
  3. 加入源碼欄位：每條規則新增「源碼來源」（程式＋function）與「源碼流程」（Mermaid），22 條一次批次補完。
  4. 一般新申裝：抽出範本：先提格式 md 與撰寫規劃，確認後才產文件；把成功案例抽成格式範本。再 review 出 10 項優化，明確要求「說清楚業務規則，而非翻譯程式」；輸出 HTML，流程圖附縮放拉桿。
  5. 包成 MCP Server：同仁在自己的 AI 工具中就能查知識庫，並規劃「有人要看才產生、產過且未變更就重用」。
  6. 信用查核 v0.1 → v0.2：先規劃、審核後撰寫；v0.1 留 5 個 ⚠；補匯入前端 JSP 後升 v0.2，UI 改依源碼 HTML、新增對外介面章。
  7. 延伸應用：針對單一規則追問（如實地訪查的源碼邏輯、購機免預繳信用燈號計算）、整理「哪些作業可併同受理」審核文件。

人負責什麼

  • 定方向：決定範圍、取捨（如「不含 NP 攜入」「規則數不設上限」）。
  • 審規劃：要求 AI「先提規劃，確認後再寫」，避免大量返工與浪費 token。
  • 挑問題：「產出很多待 BA 補充，是你不知道，還是特意留給 BA？」逼 AI 區分查不到與不該猜。
  • 守品質：審核通過才入庫；草稿不進知識庫。

14. 練習：逆向一個你熟悉的頁面

挑一個你常被問「為什麼被擋」的頁面，在已接上知識庫的 AI 工具中完成以下步驟（約 60 分鐘）：

  1. 用提示詞 ① 定位頁面，記下頁面程式與入口來源。
  2. 用提示詞 ② 取得規劃，至少修正一個範圍或問題的決定後再核准。
  3. 只撰寫一個子頁的規則（提示詞 ③），挑一條 R 規則對照源碼確認判斷邏輯。
  4. 用提示詞 ⑥ 稽核完整性，補上遺漏的阻擋點。
  5. 用檢查清單自評，並寫一筆文件歷程。

完成標準：子頁的每個阻擋點都有規則；任選一條規則，業務能看懂判斷邏輯、開發能在 1 分鐘內用源碼來源找到程式。
