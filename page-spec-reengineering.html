網頁功能 Reengineering

用知識庫＋AI 逆向解讀既有網頁，產出業務看得懂、開發找得到程式的功能規格書（Page Spec）。

源碼是唯一事實規則可追溯✅／⚠ 誠實標示

為什麼要逆向

比較原有規格文件Page Spec
描述系統「應該」做什麼系統「實際」做了什麼
方向需求驅動，由上而下源碼驅動，由下而上
痛點／解法多次修改後與程式不一致每條規則附源碼定位，可回查

事實優先序：源碼 ＞ 資料庫 ＞ 畫面 ＞ 規格文件 ＞ 推測。規格文件只作輔助。

知識庫如何建立，請見 知識庫分享。

製作流程：6 步

  1. 定位頁面：用業務關鍵字（如「風險」「欠費」）查知識庫，找出入口、子頁與呼叫鏈。先確認前端與後端源碼都已匯入。
  2. 先規劃再撰寫：請 AI 提出範圍、頁面清單與規則草估，審核通過才開寫。
  3. 由 UI 窮舉規則：從每個按鈕、欄位往下追；每個阻擋點都要對應一條規則。
  4. 業務語言＋三重定位：判斷條件寫業務意義，不貼程式；程式細節放「源碼來源」欄。三重定位＝方法名＋搜尋關鍵字＋基線行號，程式改版仍找得到。
  5. 標示驗證狀態：✅ 已對照源碼；⚠ 待驗證。不以推論冒充事實。
  6. Review 迭代：逐項消化 ⚠、依源碼 HTML 重繪畫面示意、補對外介面，記錄文件歷程。

規格書結構

章節內容
全局導覽流程圖、頁面串接圖、範圍地圖、依角色閱讀指南
作業概觀業務定位、術語、業務情境、頁面清單、規則分布
各頁規格頁面說明、畫面示意、欄位、規則（依操作時序排列）
收尾對外介面、驗證狀態、文件歷程

規則命名

R 阻擋　F 功能　D 動態顯示　X 跨系統。代號＝類型－作業－序號，例如 R-CK-101。

規則欄位

代號、業務背景、觸發時機、判斷邏輯、失敗訊息、源碼來源、源碼流程（≤ 8 節點）、資料來源、驗證狀態。

範例：信用查核（去識別化）

信用查核是多個受理作業共用的受理前預審閘門：4 個區塊同時查核，全部通過才放行，部分情況須主管複核。

受理作業（多個入口）
   ↓
信用查核框架頁
   ├ 風險查核 ── 外部風險查詢
   ├ 帳單彙寄 ── 帳務系統
   ├ 欠費查核 ── 帳務系統
   └ 企業實地訪查提示
   ↓
全部通過 → 繼續受理；須複核 → 主管確認後放行

盤點結果：5 頁、18 條規則（R×3／F×10／D×4／X×1）。

規則卡：R-CK-101 風險種類禁止受理

欄位內容
業務背景特定高風險種類（如詐騙相關）一律不受理，不開放主管複核。
觸發時機風險查詢完成、判定風險等級時。
判斷邏輯
  1. 客戶命中「禁止受理」類風險種類。
  2. 符合特定代辦例外者移除該風險，否則標記不可受理。
失敗訊息「此客戶的風險種類，系統不予受理！」
源碼來源查核主控程式．風險等級判定方法｜關鍵字：禁止受理分支｜基線行號（內部版本保留，公開版省略）
資料來源設計規格「禁止受理風險種類」章節
驗證狀態✅ 已逐碼比對源碼

好規則的樣子：業務看得懂判斷邏輯，開發用源碼來源 1 分鐘內找到程式。

提示詞範本

① 定位與規劃
請查知識庫，以「[業務關鍵字]」找出相關頁面與呼叫鏈，
依 Page Spec 範本提出規劃：範圍、頁面清單、預估規則。先不要撰寫。

② 撰寫規則
規劃核准。請從每頁 UI 觸發點往下窮舉，每個阻擋點寫一條規則；
判斷邏輯用業務語言，源碼來源用三重定位；未查證者標 ⚠。

③ 驗證補強
列出所有 ⚠ 項，逐項查源碼補證據；查不到的請誠實說明，不要推測。

檢查清單

  • ☐ 每個 UI 阻擋點都有對應規則
  • ☐ 判斷邏輯為業務語言，沒有貼程式碼
  • ☐ 每條規則有三重定位與 ✅／⚠ 狀態
  • ☐ 失敗訊息逐字取自源碼
  • ☐ 文件歷程記錄每版修改

對外分享前先去識別化：移除程式、類別與方法名稱、行號、系統代碼、文件編號、資料表欄位與人員資料，改用泛稱。
