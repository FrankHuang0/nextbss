大型專案重構：用 Superpowers 讓 AI 照 SOP 做事

AI 很會寫程式，但常常「沒問清楚就動手、沒測試就說完成」。小功能還好，大型重構一出錯就很難收拾。本課從零開始，一步一步帶你認識 Superpowers——一套讓 AI 照標準流程（SOP）做事的 Skill 組合，最後再把它用在大型專案重構。

學習路線：由淺入深

不用一次全懂。照順序走，每一步只多學一點點：

  1. 入門（第 1–3 步，約 15 分）：看懂為什麼需要 Superpowers，裝好它，確認它會動。
  2. 核心（第 4–8 步，約 30 分）：認識 7 站流水線，學會每一站你要做什麼決定。
  3. 進階（第 9 步，約 15 分）：把整套流程用在「幾萬行舊系統」的大型重構。

名詞小辭典：Skill = 寫給 AI 看的一份 SOP 說明書；重構 = 外部行為不變、只改內部寫法；子代理 = AI 另外派出去做單一小任務的「分身」。

第 1 步：先看差別——AI 為什麼需要 SOP？

同一句需求：「給使用者模組加一個批次匯出功能」。

❌ 沒有 SuperpowersAI 馬上開始寫程式。寫完才發現：格式不是你要的、沒有分頁、資料一多就把記憶體撐爆。
✅ 有 SuperpowersAI 先問：要 CSV 還是 Excel？資料量多大、要不要背景執行？誰有權限匯出？接著給 2–3 個方案讓你選，確認後才動手。

比喻：想像新來的廚師手藝很好，但不看單、不試味道就出菜。Superpowers 就是貼在廚房牆上的 SOP：先確認點單 → 備料 → 照食譜做 → 試味道 → 由店長決定出不出菜。

重點：Superpowers 不會讓 AI 變聰明，而是讓 AI 不跳步驟。大部分「AI 改壞了」都是因為跳了某一步。

第 2 步：Skill 是什麼？

Skill 是一份 Markdown 說明書（SKILL.md），寫著「遇到什麼情況、要照哪些步驟做、哪些事不准做」。Superpowers 就是一整組這種說明書，加上一條總規則（using-superpowers）：

  1. 你有一組 Skill 可以用。
  2. 開始任何工作前，先找有沒有適用的 Skill。
  3. 只要有適用的 Skill，就必須照著做——是規定，不是建議。

所以你不用背指令。你正常講需求，AI 會自己挑出對應的 Skill。常用的分成 4 類：

類別Skill白話說明
協作流程brainstorming、writing-plans、executing-plans、subagent-driven-development、using-git-worktrees、requesting-code-review、finishing-a-development-branch從「問清楚」到「交付」的整條流水線
測試test-driven-development先寫測試，再寫程式
除錯與驗證systematic-debugging、verification-before-completion找到根本原因才修；沒證據不准說完成
進階writing-skills自己寫新的 Skill（之後再學）

第 3 步：安裝與確認

以 GitHub Copilot CLI 為例，在終端機輸入兩行（英文原版）：

copilot plugin marketplace add obra/superpowers-marketplace
copilot plugin install superpowers@superpowers-marketplace

想要中文說明的版本，可改用中文增強版（會裝到目前的專案資料夾）：

npx superpowers-zh --tool copilot

公司網路：下載前要先設好 proxy 環境變數（做法見〈Copilot 桌面版入門〉），否則會卡在下載。

確認它會動：開一個新對話，輸入「幫我做一個待辦清單網頁」。

  • ✅ 正常：AI 先問你問題（要存在哪裡？要不要登入？），而不是直接寫程式。
  • ❌ 異常：AI 直接開始寫程式碼 → 代表 Skill 沒載入，重開程式或檢查安裝。

完成標準：新對話裡，AI 會先問問題、提方案，才開始寫程式。

第 4 步：認識 7 站流水線

Superpowers 把「叫 AI 寫程式」拆成 7 站。先看全貌，下面幾步再一站一站講：

  1. brainstorming 問清楚、出設計
  2. using-git-worktrees 開隔離工作區
  3. writing-plans 拆成小任務
  4. 執行 subagent-driven-development 或 executing-plans
  5. test-driven-development 每個任務先寫測試
  6. requesting-code-review 任務之間審查
  7. finishing-a-development-branch 由你決定怎麼合併

比喻：像蓋房子——先跟屋主談需求（1）、圍起工地不影響鄰居（2）、畫施工圖（3）、按圖施工（4）、每道工序都驗收（5、6）、最後由屋主決定交屋（7）。

新手常誤會實際上
7 站是一條直線，最後再補測試第 5、6 站在每個任務裡都跑一次：測試 → 實作 → 審查，通過才做下一個
using-git-worktrees 只是開個資料夾開好後會先跑一次全部測試，確認「起點是綠的」，之後紅燈才看得懂
測試全綠 AI 就可以自己合併合併、開 PR、保留或丟棄，一定由你選

第 5 步：brainstorming——先分類，再問清楚

brainstorming 第一件事是判斷需求屬於哪一類，因為不同類要走的流程長短不同：

類型什麼時候流程
Spike 探路只想知道「能不能做、值不值得」做個小實驗、給結論，程式碼丟掉
Bounded 小改改的流程在專案裡已經存在問幾題 → 對話中給短設計 → 你說 OK → 動手
Architectural 新架構專案裡還沒有這條流程一次問一題 → 2–3 個方案 → 分段確認 → 寫成設計文件 → 你審過 → 寫計畫

判斷只看一句：「這條流程，現在在這個專案裡讀得到嗎？」看的是專案，不是任務大小。做到一半發現比想像複雜，只能往上升級（Spike → Bounded → Architectural），不能往下降。

範例：在已經有待辦清單的專案裡，加「匯出成 CSV」（Bounded）：

  1. 你

    「幫待辦清單加一個匯出成 CSV 的按鈕。」

  2. Copilot

    這是 Bounded：匯出會用到現有的清單資料。先確認一題：已完成的項目要一起匯出嗎？

  3. 你

    「要，多一欄標示是否完成。」

  4. Copilot

    設計：按鈕放在清單上方，欄位為「標題、到期日、是否完成」，檔名含日期。這樣可以嗎？

  5. 技巧

    AI 一次只問一題、會附建議答案。不確定就回「用你的建議」，但要看完再回。

  6. 你

    「可以。」

  7. Copilot

    收到，開始實作。

  8. 技巧

    你說「可以」只代表同意眼前這一段。如果是 Architectural，下一步應該是寫設計文件給你審，不是直接寫程式。

第 6 步：writing-plans——計畫要寫到實習生也能照做

設計確認後，writing-plans 會把它拆成很多2–5 分鐘就能做完的小任務。每個任務寫清楚：改哪個檔案、完整程式碼、怎麼驗證、預期結果。

比喻：想像接手的是一位「技術不錯，但完全不懂這個專案、品味可疑、又討厭寫測試的實習生」。計畫要寫到他照著做也不會做錯——AI 子代理就是這種讀者。

計畫裡出現下面這些字眼，就是還沒寫完，要退回：

看到問題
TBD、TODO、之後再補把決定丟給執行的人
「加上適當的錯誤處理」「適當」是什麼，沒人知道
「為上面的功能寫測試」卻沒有測試碼沒有測試碼 = 沒有規格
「同任務 2」執行者可能只讀這一個任務
只說要做什麼，沒給程式碼文字描述不夠精確
用了前面沒定義的函式名稱執行者只好自己編一個
❌ 看起來對的計畫任務 2：寫註冊功能，加上適當的檢查，並為上面的功能寫測試。
✅ 能交付的計畫任務 2：建立 register.ts 與測試檔；附 3 個測試（email 沒有 @ → INVALID_EMAIL；密碼少於 12 碼 → WEAK_PASSWORD；正確 → 回傳 userId）；驗證指令 npm test，預期先 3 個失敗。

第 7 步：執行——每個任務都「先紅後綠」

test-driven-development（TDD）只有 3 個動作，每個任務都照做：

  1. RED 紅燈 先寫測試，執行，確認它失敗
  2. GREEN 綠燈 寫最少的程式讓測試通過
  3. REFACTOR 整理 測試保持綠燈，把程式整理乾淨

為什麼要先看到紅燈？如果測試一開始就通過，代表它根本沒測到新功能。先寫程式再補測試的，Superpowers 會要求刪掉重來。

執行方式有兩種，計畫寫完 AI 會問你選哪一種：

subagent-driven-developmentexecuting-plans
做法每個任務派新子代理實作，再派另一個子代理審查（先看有沒有照規格、再看程式品質）在同一個對話裡依序做完，最後整體審查一次
優點最徹底；前一個任務的錯不會帶到下一個最省 token、最快
適合任務多（約 10 個以上）、出錯代價高、想讓 AI 自己跑很久5 個以內的小任務、計畫已經很清楚

requesting-code-review 會在任務之間檢查：發現嚴重問題就擋住，修好才能往下做。

第 8 步：驗證與收尾——沒有證據，不准說完成

verification-before-completion 的鐵律：沒有剛剛跑出來的驗證結果，就不能說「完成」。上一輪跑過的不算，改過檔案就要重跑。

  1. 找出能證明的指令（例如跑全部測試）。
  2. 完整執行一次。
  3. 讀完輸出：失敗幾個？結束碼是多少？
  4. 輸出真的支持「完成」嗎？不支持就照實說。
  5. 最後才說「完成」，並附上證據。
❌ 紅旗說法「應該好了」「看起來沒問題」「子代理說測試都過了」
✅ 有證據的說法「剛跑完 npm test：42 個通過、0 個失敗，輸出如下……」

收尾：finishing-a-development-branch 會先跑測試，再給你選項——合併回主線、推上去開 PR、先保留分支、或丟棄。由你選；要丟棄必須你親口說。

卡住時：systematic-debugging 要求先找到根本原因再修（重現 → 找規律 → 提假設驗證 → 修正並加測試），不准亂猜亂改。如果是 Superpowers 本身怪怪的，就問 AI：「幫我找出這個對話裡 superpowers 哪裡出問題」。

第 9 步：進階——用 Superpowers 做大型專案重構

前 8 步學的是「做好一個功能」。大型重構（例如幾萬行的舊模組換語言、換架構）只是把同一套流程重複很多次，再加 2 個觀念：

觀念白話說明
絞殺榕（Strangler Fig）不要一次全部重寫。新系統像絞殺榕一樣慢慢長在舊系統外面，一次取代一小塊，舊的繼續運作，直到全部換完。
特徵化測試（黃金測試）先把舊系統「現在的行為」錄下來當標準答案：同樣的輸入，記下輸出。新程式的輸出要和這份黃金樣本一模一樣，才算沒改壞。

和 7 站流水線對起來：

  1. 第 0 輪 brainstorming 屬於 Architectural：先切出批次路線圖，每批小到能單獨驗收
  2. 每一批 新開對話，重新跑一次 brainstorming → writing-plans
  3. 計畫第一個任務 先寫特徵化測試，鎖住舊行為
  4. 執行 任務多、代價高，選 subagent-driven-development
  5. 收尾 新舊輸出逐項比對、附證據，再決定合併
❌ 一次叫 AI 重寫整個模組對話塞爆、AI 開始忘記前面的規則；出錯時不知道是哪裡壞。
✅ 一批一批取代每批一份計畫、一個新對話、一組特徵化測試；壞了只影響一小塊，馬上找得到。
人負責AI 負責
決定批次順序、回答需求問題、選執行方式、決定合併讀舊程式、計數與整理、寫設計和計畫、寫測試與程式、跑驗證

安全提醒：資料庫只給 AI 唯讀權限；帳號密碼、proxy 設定放個人設定檔，不進 repo；不可逆的操作（刪資料、推到共用分支）一定由人執行或確認。

自我檢核：5 題

1. 裝好之後，要怎麼知道 Superpowers 有在運作？

開新對話提一個需求。AI 先問問題、給方案，而不是直接寫程式，就代表 brainstorming 有被觸發。

2. 專案裡已經有登入功能，要加「PIN 碼快速登入」，屬於哪一類？

Bounded。登入流程已經在專案裡，你是在改它。如果專案原本完全沒有登入，才是 Architectural。

3. 計畫寫著「加上適當的驗證」，哪裡有問題？

「適當」沒有定義。要寫出具體的輸入、預期結果和測試碼，否則每個執行者會照自己的品味亂補。

4. 子代理回報「任務完成、測試全過」，可以直接做下一個嗎？

不行。自己回報不算證據。要看程式差異、自己重跑一次測試，看到實際輸出才算。

5. 大型重構為什麼要先寫特徵化測試？

先鎖住舊行為。舊系統的細節常常連文件都沒寫。先把「同樣輸入 → 什麼輸出」錄成黃金樣本，新程式對得上才能證明沒改壞。

重點回顧

  • Superpowers 不讓 AI 變聰明，而是讓 AI 不跳步驟：有適用的 Skill 就必須照做。
  • 7 站流水線：問清楚 → 隔離 → 寫計畫 → 執行 → 每任務 TDD → 任務間審查 → 由你決定合併。
  • 先分類：Spike、Bounded、Architectural，看「專案裡有沒有這條流程」。
  • 計畫不能有 TBD 和空泛字眼；每個任務先紅後綠；沒有證據不准說完成。
  • 大型重構 = 絞殺榕分批取代 + 特徵化測試鎖住舊行為 + 每批重跑一次流水線。
